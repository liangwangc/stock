## 设置页面功能与逻辑问题汇总（阶段性草稿）

> 说明：本文件只记录目前已经详细审查过的模块和问题，后续审查其他模块时会继续往下追加。当前覆盖模块：  
> - 模型学习相关（性能评估 / 回测 / 参数优化）  
> - 参数设置（panel-params）  
> - 备份管理（panel-backup）  
> - 模型训练（panel-model-training）  
> - 股票分析任务管理（panel-task）  
> - 新闻抓取（panel-news）  
> - 股票/其他数据获取（panel-stock-data）  
> - 定时任务管理（panel-scheduled-tasks）

### 一、模型学习相关功能

对应位置：
- 后端：`web_app.py` 中 `/api/model/evaluate`、`/api/backtest/run`、`/api/model/optimize` 等路由  
- 后端：`utils/model_performance_evaluator.py`、`utils/backtest_engine.py`、`utils/model_optimizer.py`  
- 前端：`templates/settings.html` 中 `panel-model-learning` 区域

#### 1. 性能评估（点击后“没结果”的问题）

- **问题 1-1：API 成功 / 失败语义不清**
  - 现象：当 **预测评估**和**交易评估**都没数据或失败时，`/api/model/evaluate` 依然返回 `success: True`，只是 `data` 里字段为空或缺失。前端拿到 `success: True` 会直接尝试渲染，而不是弹出错误提示，用户体验就是“点了没反应”。
  - 影响：  
    - 用户无法区分“评估真的没问题”与“实际上根本没有可评估的数据”。  
    - 前端逻辑会继续访问缺失字段，进一步引出 NaN 等显示问题。

- **问题 1-2：前端对缺失字段缺乏容错**
  - 现象：`displayPerformanceResults` 中直接使用 `data.direction_accuracy * 100`、`data.win_rate * 100` 等表达式，若字段不存在或为 `undefined`，结果为 `NaN`，最终展示为 “NaN%”。  
  - 影响：  
    - 当后端没有返回某些字段时，页面指标卡、图表会出现 NaN，肉眼不一定马上发现，容易误解为系统“没更新数据”。

> 现状：上述问题在最近一次调整中已经修复，但这里仍保留为历史问题记录，方便后续回顾设计。

#### 2. 回测功能（“效果很差”的问题）

- **问题 2-1：早期版本中，买入成本字段混淆，导致收益率严重失真**
  - 早期逻辑（问题版本）：  
    - 买入时将“总成本”直接写入 `cost_price` 字段；  
    - 卖出时用“每股价格”与 `cost_price` 比较来计算收益率。  
    - 示例：买入总成本约 30000 元，`actual_price` 约 25.5 元，公式变成 `(25.5 - 30000)/30000`，得到约 -99.9% 的“巨亏”，几乎所有交易都会被算成极端亏损。
  - 影响：  
    - 回测曲线高度悲观，夏普比率、最大回撤等所有基于收益率的指标都严重失真。  
    - 用户直观感受就是“回测一塌糊涂”，对模型完全失去信心。

- **问题 2-2：持仓估值逻辑过于简化**
  - 早期 `_calculate_portfolio_value` 使用 **成本价** 估算持仓市值，而不是实际市场价格。  
  - 影响：  
    - 最大回撤、日度收益序列、夏普比率等全部偏离真实情况。  
    - 即使单笔交易利润逻辑正确，组合层面的风险收益表现仍然严重走样。

- **问题 2-3：前端再次放大利润百分比（双重 *100）**
  - 后端回测指标（尤其是 `metrics.total_return`、`metrics.win_rate`、`metrics.max_drawdown` 等）本身已经是百分比数值（5.23 表示 5.23%）。  
  - 前端 `renderBacktestResults` 中又把这些值乘以 100 再显示，导致视觉上变成 523.00%。  
  - 影响：  
    - 用户会误以为策略极端波动（要么爆亏要么爆赚），进一步削弱对回测结果的信任。

> 当前版本：成本价/估值/百分比重复缩放等问题已经修复；这里记录为设计缺陷历史。

#### 3. 参数 / 权重优化

- **问题 3-1（设计层面致命）：优化器搜索的参数在回测引擎中根本没用上**
  - 早期版本设计：  
    - `ModelOptimizer` 默认搜索的是一组“权重参数”，如：`news_weight`、`capital_flow_weight`、`market_weight`、`technical_weight`、`history_weight` 等。  
    - 但 `BacktestEngine.backtest_with_parameters` 实际只读取以下**交易参数**：  
      - `buy_threshold`（买入阈值）  
      - `sell_threshold`（卖出阈值）  
      - `min_confidence`（最小置信度）  
      - `stop_loss_pct`（止损）、`take_profit_pct`（止盈）  
      - `max_position_pct`（仓位比例）  
    - 权重相关字段在回测引擎中完全没有被读取或使用。
  - 直接后果：  
    - 无论 `ModelOptimizer` 如何调整权重组合，回测引擎都在用“同一套交易参数”做回测，结果曲线几乎一样。  
    - “最优权重组合”实际上只是从一堆结果极其相似的回测里，随机挑了一个分数略高的，优化过程名存实亡。

- **问题 3-2：优化评分函数量纲不一致，夏普比率被极度放大**
  - 早期 `_calculate_optimization_score` 的结构大致为：  
    \[
    \text{score} = total\_return * 0.4 + sharpe\_ratio * 0.3 + (1 - max\_drawdown) * 0.2 + win\_rate * 0.1
    \]
  - 问题在于：  
    - `total_return`、`win_rate`、`max_drawdown` 等都在 0~1 的小数级别；  
    - `sharpe_ratio` 通常在 [-1, 3] 区间。  
    - 在没有归一化的情况下，夏普比率对得分的影响远大于其他指标，导致优化器几乎只追求“看起来夏普比率高”的解。
  - 实际效果：  
    - 优化出的参数组合在风险/收益/胜率上的表现不一定更好，只是某些样本上的夏普被抬高。  
    - 用户从实际回测曲线体感不到“明显变好”，会觉得“优化没啥用”。

### 二、参数设置模块（panel-params）

对应位置：
- 后端：`utils/prediction_config_manager.py`  
- 前端：`templates/settings.html` 中 `panel-params` 区域及相关 JS 函数

#### 1. 权重校验标准前后端矛盾（致命）

- 后端验证逻辑：  
  - `validate_config` 要求 5 个传统因子权重（`news_weight`、`capital_flow_weight`、`market_weight`、`technical_weight`、`history_weight`）之和 **必须为 1.0（±0.01 容差）**。
- 前端引导文案 & 校验逻辑：  
  - 文案提示：“传统因子权重之和约为 0.65，另 0.35 由 ML 模型贡献”。  
  - 前端用 0.65 作为“绿色通过”的判断标准。  
- 结果：  
  - 用户按照前端文案设置出的“合理权重”在后端校验总是失败。  
  - 即使前端显示“权重合计 0.65 ✔”，后端依然报“权重总和应为 1.0”，**导致配置永远无法通过后端校验并激活**。

#### 2. `performance` 分类参数读取时被静默丢弃（严重）

- 后端 `_get_param_definitions` 中定义了 `performance` 分类的一系列参数（如历史任务最大并发、预测缓存最小持续时间等）。  
- `_save_config_values` 能将这些参数正确写入 `prediction_config_values`。  
- 但 `get_config` 初始化时只创建了：`prediction`、`indicator`、`news`、`trading` 四个 key，没有 `performance`。  
- 后续从数据库读出 `category = 'performance'` 的记录时，由于 `category not in config_dict`，被直接忽略。  
- 影响：  
  - 相关参数可以被保存到数据库，但在读取到内存配置结构时全部丢失。  
  - 前端如果未来添加 UI 来编辑性能相关参数，也会出现“保存后读不回来”的现象。

#### 3. X2 指标参数保存路径缺失（严重）

- 前端 `loadConfigValues` 和默认配置加载中都有 X2 相关字段（阈值与得分共计 8 个）。  
- 但 `getCurrentConfigValues` 收集要提交的配置时，只列出了传统技术指标参数（MA/RSI/MACD/KDJ/CCI），完全遗漏 X2 系列参数。  
- 实际效果：  
  - X2 参数可以展示、可以被用户修改，但点击“保存配置”后，这些参数不会出现在提交 payload 中。  
  - 下一次重新打开设置页面时，X2 相关字段恢复为默认值或旧值，用户以为“系统没记住我刚才的设置”。

#### 4. 部分交易参数前端有，后端无定义（严重）

- 前端在 `getCurrentConfigValues` 中收集了若干交易相关参数，如：  
  - `max_total_position_pct`（组合总仓位上限）  
  - `max_correlation`（持仓相关性上限）  
  - `enable_risk_control`（是否启用风险控制）  
- 但在后端 `_get_param_definitions` 的 `trading` 分类中，没有对应 key 的定义。  
- 结果：  
  - `_save_config_values` 会遍历所有提交参数，只对已在 `param_definitions` 中登记的键执行 INSERT。  
  - 这几个额外的交易参数被直接 `continue` 掉，相当于用户做的修改从未真正进入数据库。

#### 5. `news` 分类前端完全缺失（严重）

- 后端定义了 `news` 分类若干配置（新闻条数、情绪阈值、是否包含行业新闻等）。  
- 前端目前没有任何针对 `news` 分类的 UI：  
  - 不展示现有值；  
  - 不允许用户修改；  
  - 也不会把 `news` 分类写回到提交值里。  
- `_save_config_values` 的策略是：  
  - 先 `DELETE FROM prediction_config_values WHERE config_id = ?`；  
  - 再插入新的分类参数。  
- 这意味着：  
  - 任何一次“只改 prediction / indicator / trading”的配置保存操作，都会把原本存在的 `news` 分类参数删掉，而且不会再写回新值，**形成“操作一次别的配置，顺带清空所有 news 配置”的副作用**。

#### 6. 配置删除历史记录被级联删除（严重）

- 删除配置流程：  
  - 先通过 `get_config` 读取当前配置值，调用 `_record_history(config_id, 'delete', old_values, None, ...)` 记录一条删除历史；  
  - 然后执行 `DELETE FROM prediction_config WHERE id = ?` 真正删除配置主记录。  
- 问题在于：  
  - `prediction_config_history` 表在建表时通过 `FOREIGN KEY (config_id) REFERENCES prediction_config(id) ON DELETE CASCADE` 与主表关联。  
  - 当删除主表记录时，会将所有引用该 `config_id` 的历史记录一并删掉。  
- 结果：  
  - 删除配置之前刚写入的 `'delete'` 操作历史马上就被级联删除了，数据库中最终没有留下任何与删除行为相关的审计记录。

#### 7. 其他设计与实现层面问题（概述）

（以下问题严重程度相对较低，这里只做摘要，详细可在后续精简为修复任务清单）

- `clear_cache(config_id=None)` 使用不可重入锁并在持锁期间调用 `get_config`，存在潜在死锁风险。  
- JS 端多处用 `value || default` 来提供默认值，导致合法的 `0` 被错误替换为默认值。  
- `_save_config_values` 的“先删后插”操作不包裹在显式事务中，异常情况下有中途失败导致部分分类参数永久丢失的风险。

### 三、备份管理模块（panel-backup）

对应位置：
- 后端：`utils/backup_manager.py`、`web_app.py` 中 `/api/backup/*` 路由  
- 前端：`templates/settings.html` 中 `panel-backup` 区域及相关 JS

#### 1. 扫描出的备份无法恢复 / 删除（严重）

- 当 metadata 中没有某条备份记录时，`list_backups` 会调用 `_scan_backup_files` 直接扫描备份目录并返回文件列表，用于前端展示。  
- 但 `restore_backup` / `delete_backup` 在查找目标时只遍历 `self.metadata['backups']`，扫描新增的备份文件没有对应的 metadata entry，因此会提示“备份 ID 不存在”，无法真正执行恢复或删除。  
- 实际效果：  
  - UI 上可以看到备份文件，但按钮点了也不生效，让人感觉“备份功能不可靠”。

#### 2. 备份 ID 生成方式容易重复（严重）

- 新备份 ID 使用 `len(self.metadata.get('backups', [])) + 1` 生成。  
- 当中间删除过某些备份（例如已有 ID:1,3），再次创建备份会得到 ID=3，与现有记录冲突。  
- 后续操作（恢复 / 删除）若以 ID 为唯一识别键，容易误操作到另一份备份。

#### 3. 并发与文件名冲突问题（中）

- 备份文件名使用时间戳 `%Y%m%d_%H%M%S`，精确到秒：同一秒内发起多次备份会覆盖同名文件。  
- 元数据读写未加锁、防并发机制，多个进程或多实例同时进行备份、删除、恢复操作时，存在竞态条件。

#### 4. 安全与体验方面的小问题（概述）

- 删除 / 恢复对话框仅用一次 `confirm` 对话框做防误操作，未提供例如“需输入完整备份名确认”等更严格防护。  
- 在前端渲染备份列表时，部分字符串（如文件名、描述）直接插入 HTML / JS 字符串模板，理论上存在 XSS 隐患（前提是攻击者能控制文件名或 metadata 内容）。

### 四、模型训练模块（panel-model-training）

对应位置：
- 后端：`web_app.py` 中 `/api/ml/train/*`、`/api/ml/models/*` 路由  
- 后端：`utils/ml_model_trainer.py`  
- 前端：`templates/settings.html` 中 `panel-model-training` 及对应 JS 函数

#### 1. 训练任务并发控制不足（高）

- 后端在启动基础训练 (`/api/ml/train/base`) 或微调训练 (`/api/ml/train/finetune`) 时，没有严格检查当前是否已经存在**同类型正在运行的任务**。  
- 前端按钮点击也未在调用前先查询当前状态并做“已有任务在运行”的拦截。  
- 结果：用户可在短时间内多次点击，意外启动多个训练任务，造成：  
  - 数据库和文件 IO 冲突；  
  - 训练日志和任务状态表 `ml_training_tasks` 内容混乱；  
  - 资源占用激增。

#### 2. 训练任务表只增不减（高）

- `ml_training_tasks` 在任务启动时 append 一条记录，任务完成或失败后并未有统一逻辑清理旧记录。  
- 服务长期运行后，内存中会保存大量历史任务信息，占用内存、影响查询效率。

#### 3. 进度反馈不真实（中）

- 训练进度在后端仅在任务开始时设置为约 5%，任务结束时置为 100%。  
- 中间执行过程不会持续更新进度。  
- 前端轮询拿到的进度长期停在 5%，直到任务结束突然跳到 100%，用户主观体验就是“进度条卡住不动，很久才一下子完成”，容易误以为应用卡死。

#### 4. 多任务状态获取逻辑不清晰（中）

- `/api/ml/train/status` 在存在多个任务记录时，仅返回第一个 `running_tasks[0]` 作为当前状态。  
- 如果基础训练和微调训练重叠，或用户连续多次操作，状态信息可能与用户当前关注的任务不一致。

### 五、股票分析任务管理模块（panel-task）

对应位置：
- 后端：`web_app.py` 中 `/api/tasks/*` 相关路由  
- 可能相关后端模块：`utils/task_history_db.py` 等任务记录工具  
- 前端：`templates/settings.html` 中 `panel-task` 区域及 `startAnalysis`、`updateTaskStatus`、`stopAnalysis`、`refreshTaskHistory` 等 JS 函数

#### 1. 任务启动阶段的问题

- **问题 T1：task_id 可能在同一秒内重复（高）**  
  - 生成规则为 `task_{YYYYMMDD_HHMMSS}`，仅精确到秒。  
  - 若同一秒内用户多次点击“开始分析”，会生成相同的 `task_id`。  
  - 后果：  
    - 后端 `running_tasks` 字典中后启动的任务会覆盖先前的记录；  
    - 数据库中以 `task_id` 为主键或唯一键的地方也可能产生覆盖，导致历史记录混乱。

- **问题 T2：任务启动存在竞态条件（高）**  
  - 当前流程是：先 `thread.start()` 启动分析线程，再在 `task_lock` 下把任务信息记录进 `running_tasks`。  
  - 如果线程启动后很快执行到“检查自己是否在 running_tasks 中”的逻辑，可能发现自身未注册，从而直接结束或执行异常路径。  
  - 后果：  
    - 前端收到“任务已启动”的响应，但实际后台线程很快退出或根本没正确登记，进度长时间停留在 0/初始值，看起来像“假启动”或“卡住不动”。

- **问题 T3：后端对同一用户的并发任务无硬限制（中）**  
  - `api_start_task` 未检查当前用户是否已有运行中的分析任务。  
  - 前端只在当前标签页内通过 `currentTaskId` 和按钮禁用来防重复点击，在多标签页或多客户端下无法限制。  
  - 后果：  
    - 同一用户可以在多标签页同时启动多份重型分析任务，造成数据库和 CPU 资源的大量竞争。

#### 2. 任务状态轮询与进度更新

- **问题 T4：状态轮询不依赖当前面板（中）**  
  - JS 使用 `setInterval`，只要 `currentTaskId` 非空就每 2 秒轮询 `/api/tasks/{task_id}`。  
  - 不判断“当前是否仍停留在股票分析任务管理面板”。  
  - 后果：  
    - 用户切换到其他设置面板后，轮询依然持续，对后端造成不必要的负载。

- **问题 T5：轮询没有超时或最大次数控制（低）**  
  - 清理轮询的唯一逻辑是 `currentTaskId` 被置空。  
  - 若异常情况下 `currentTaskId` 未被正确清空，轮询会一直运行下去。  

- **问题 T6：进度更新存在一定滞后但可接受（低）**  
  - 后端为减少消息量，常常每处理若干股票才 emit 一次进度事件；  
  - 在股票数量较多时，前端看到的进度会以“阶梯”形式前进，不是平滑曲线。  

#### 3. 任务停止与权限控制

- **问题 T7：停止任务缺少用户级权限校验（高）**  
  - `api_stop_task` 仅校验用户是否已登录，并未校验该 `task_id` 是否属于当前用户（例如 `task.user_id == session['user_id']`）。  
  - 后果：  
    - 任何登录用户只要知道一个合法 `task_id`，就可以停止他人的任务，属于典型的越权操作风险。

- **问题 T8：停止标记与任务记录不清理（高）**  
  - 任务结束（成功 / 失败 / 被停止）后，`running_tasks` 和 `task_stop_flags` 中对应条目没有统一的清理逻辑。  
  - 后果：  
    - 服务长期运行后，这两个结构会不断膨胀，造成内存浪费；  
    - 某些内部逻辑以“是否存在于 running_tasks / task_stop_flags”来判断当前状态时，可能被过期记录误导。

- **问题 T9：多次停止同一任务的语义不清晰（低）**  
  - 再次调用停止接口时，后端返回“无法停止，任务状态不是 running”，但不会造成更严重的问题。  

#### 4. 历史记录与可见性

- **问题 T10：历史记录未按用户隔离（高）**  
  - `/api/tasks/history` 在查询历史时，只按时间排序和 limit 限制，SQL 中没有 `WHERE user_id = ?` 过滤条件。  
  - 后果：  
    - 任意登录用户可以看到所有用户的任务历史（包括其他人的分析范围、股票池、时间等信息），存在数据隐私和权限边界问题。

- **问题 T11：前端历史列表列内容与表头含义不匹配（中）**  
  - “分析类型”“分析内容”等表头对应的列实际填入的是 `limitText`（数量）、`sortText`（排序方式），而不是抽象后的“按数量 / 按股票”“分析维度”等。  
  - 影响：  
    - 用户阅读历史记录时难以快速理解每一列的含义，降低可用性。

- **问题 T12：历史记录没有分页（中）**  
  - 前端固定请求 `limit=50`，没有 offset / page 参数；后端也只实现了简单的 limit。  
  - 后果：  
    - 只保留最近 50 条记录的可见性，更早的历史分析任务对用户来说等同于“丢失”，不利于长期使用和审计。

#### 5. 并发与多客户端场景

- **问题 T13：多标签页 / 多客户端下的状态广播与过滤（中）**  
  - 后端通过 WebSocket 广播任务事件（task_started / task_completed / task_cancelled）给所有连接。  
  - 前端依赖 `task_id === currentTaskId` 来过滤“当前关心的任务”。  
  - 在多标签页或多用户场景下，可能存在某个标签页接收到与自身无关的任务事件、短暂显示不一致状态的情况。

### 六、新闻抓取模块（panel-news）

对应位置：
- 后端：`web_app.py` 中 `/api/news/tasks*`、`/api/news/llm/*` 路由  
- 后端：`utils/news_task_manager.py` 及新闻抓取相关模块  
- 前端：`templates/settings.html` 中 `panel-news` 区域及任务管理 / LLM 分析相关 JS 函数

#### 1. 任务管理（增删改查）中的关键问题

- **问题 N1：删除任务只删旧表，不删统一调度主表（致命）**  
  - `delete_task()` 仅删除 `news_crawl_tasks`，未同步删除 `scheduled_tasks` 中对应记录。  
  - 后果：  
    - 用户删除后列表里任务可能仍出现；  
    - 调度器仍可能继续执行“已删除”任务，形成强一致性问题。

- **问题 N2：更新任务只更新旧表，不更新统一调度主表（致命）**  
  - `update_task()` 仅更新 `news_crawl_tasks`，而查询展示通常优先读 `scheduled_tasks`。  
  - 后果：  
    - 用户编辑任务后，界面和实际调度仍按旧配置执行；  
    - 用户会感知为“修改不生效”。

- **问题 N3：删除前未先停止调度器中的任务（中）**  
  - 删除逻辑未显式调用统一调度器的 stop/unregister 流程。  
  - 后果：  
    - 在某些状态下任务删除后仍可能被调度线程触发。

#### 2. 调度与参数逻辑问题

- **问题 N4：`hourly` 模式忽略 `interval_minutes`（高）**  
  - 创建任务时允许填写分钟间隔（例如 90 分钟），但 `hourly` 调度分支实际上按“每 1 小时”固定执行。  
  - 后果：  
    - 用户配置“每 1.5 小时”会被静默改成“每 1 小时”，执行频率与预期不符。

- **问题 N5：`interval_minutes` 小数值健壮性不足（中）**  
  - 调度库对整数间隔更稳定；当前流程允许小数输入，边界场景下可能调度异常。  
  - 后果：  
    - 间隔可能被隐式取整、报错或出现不可预测行为。

#### 3. LLM 分析链路问题

- **问题 N6：LLM 分析启动存在竞态，可重复启动（高）**  
  - 启动接口中，状态从检查到置为 running 之间存在窗口期，第二个请求可能穿透检查。  
  - 后果：  
    - 同时运行多个 LLM 分析进程，出现资源竞争与结果覆盖。

- **问题 N7：子进程模式进度不可实时更新（高）**  
  - 回退到 `subprocess` 执行时，日志与进度是“结束后一次性读取”，中间无法细粒度更新。  
  - 后果：  
    - 前端进度条长期停在 0 或低值，用户误判为“卡住”。

- **问题 N8：进度回退算法可能引用全局统计导致失真（中）**  
  - 在部分状态下用全局“已分析/未分析数量”推断本次任务进度，范围不一定匹配当前任务。  
  - 后果：  
    - 进度可能跳变、提前 100% 或长期不动。

- **问题 N9：前端轮询异常时未稳妥停止（中）**  
  - 轮询链路在异常分支下仍可能继续触发下一次检查。  
  - 后果：  
    - 失败后仍持续请求状态接口，增加后端负担。

#### 4. 权限与多用户隔离

- **问题 N10：任务操作与 LLM 分析缺少细粒度权限隔离（中）**  
  - 当前主要做“是否登录”校验，未细分管理员/普通用户能力，也缺少明确的多租户隔离。  
  - 后果：  
    - 多用户环境下容易出现误操作或越权风险。

#### 5. 前端交互与一致性问题（次要）

- **问题 N11：编辑接口未传 `sources`，后端却允许更新该字段（中）**  
  - 前后端字段设计不一致，后续扩展容易踩坑。  

- **问题 N12：关闭编辑弹窗使用宽泛选择器（低）**  
  - 可能误关闭其他固定定位弹窗，造成交互异常。

### 七、股票 / 其他数据获取模块（panel-stock-data）

对应位置：
- 后端：`web_app.py` 中 `/api/stock-data/tasks*`、`/api/other-data/tasks*`、`/api/scheduled/tasks*`（source=scheduled_tasks）  
- 后端：`utils/scheduled_task_manager.py`（任务历史、调度执行）  
- 前端：`templates/settings.html` 中 `panel-stock-data` 区域及相关 JS 函数

#### 1. 任务创建与调度参数问题

- **问题 SD1：月度调度参数链路不完整（高）**  
  - 股票数据任务支持“monthly”类型，但前端创建表单未提供 `schedule_month_day` 输入，后端创建接口也未完整消费该参数。  
  - 后果：  
    - 用户无法配置“每月几号执行”，任务会退化为固定默认日期执行（通常是每月1号），与预期不符。

- **问题 SD2：其他数据任务对必需参数校验不充分（中）**  
  - 某些任务类型（如融资融券、主力资金、行业信息）理论上需要明确股票列表或相关参数，但创建接口未强制校验。  
  - 后果：  
    - 任务可成功创建，但运行时才暴露缺参失败，造成“创建成功但执行报错”的延迟故障。

#### 2. 历史记录链路问题（影响可用性）

- **问题 SD3：历史接口 `limit=None` 会触发 SQL 风险（致命）**  
  - 任务历史 API 在某些调用路径下将 `limit=None` 传给底层 `get_task_history()`；SQL 使用 `LIMIT %s` 时若传入 None 可能导致异常。  
  - 后果：  
    - 历史记录接口返回失败或空数据，页面出现“有任务但看不到历史”。

- **问题 SD4：前端历史数据是“截断式拉取”（高）**  
  - 前端先请求最多 1000 条任务，再对每个任务最多拉 100 条历史，本地再合并分页。  
  - 后果：  
    - 当任务量/历史量较大时，实际展示是“被截断后的子集”，不是完整历史；用户误以为数据丢失。

- **问题 SD5：历史耗时字段映射错误（高）**  
  - 前端显示使用 `item.duration`，而后端字段通常为 `duration_seconds`（或其他命名），映射缺失。  
  - 后果：  
    - UI 显示 `undefined秒` 或空值，影响历史记录可读性。

#### 3. 前后端类型映射与展示问题

- **问题 SD6：其他数据任务类型前缀不一致（致命）**  
  - 前端名称映射按 `other_data_collection_*`，后端真实类型是 `other_data_*`。  
  - 后果：  
    - 任务列表中“其他数据任务”无法正确翻译为中文名称，直接显示技术名，影响理解与运维判断。

#### 4. 交互与健壮性问题（次要）

- **问题 SD7：任务启动/停止按钮缺少防重复点击（低）**  
  - 短时间多次点击可能触发重复请求。  

- **问题 SD8：stock-data 任务列表刷新无显式 loading（低）**  
  - 请求慢时用户容易误判为页面卡住。  

- **问题 SD9：编辑/创建弹窗关闭选择器过于宽泛（中）**  
  - 使用 `querySelector('div[style*=\"position: fixed\"]')`，可能误关闭其他弹窗。

#### 5. 性能层面问题

- **问题 SD10：后端先全量取任务再内存过滤（低）**  
  - `/api/stock-data/tasks` 先取全部任务，再在 Python 端筛选 stock/other_data 类型。  
  - 后果：  
    - 任务量大时响应变慢，CPU与内存浪费。

### 八、定时任务管理模块（panel-scheduled-tasks）

对应位置：
- 后端：`web_app.py` 中 `/api/scheduled/tasks*`、`/api/scheduled/scheduler/status` 等路由  
- 后端：`utils/scheduled_task_manager.py`  
- 前端：`templates/settings.html` 中 `panel-scheduled-tasks` 区域及 `refreshScheduledTasks`、`startScheduledTask`、`stopScheduledTask`、`deleteScheduledTask`、`editScheduledTask` 等 JS 函数

#### 1. 多来源任务操作未传递 source 参数（致命）

- **问题 ST1：前端启动/停止/删除/编辑均不传 task_source**
  - `get_all_tasks` 返回混合任务：来自 `scheduled_tasks`、`news_crawl_tasks`、`analysis_tasks` 三张表，每个任务带有 `_source` 字段标识来源。
  - 但 `startScheduledTask`、`stopScheduledTask`、`deleteScheduledTask`、`editScheduledTask` 调用 API 时均未传递 `source` 参数。
  - 后端 `delete_task` 在 `task_source=None` 时：先 `get_task(task_id)`（只查 `scheduled_tasks`），对 news/analysis 任务返回 None，于是 `task_source` 默认 `'scheduled_tasks'`，执行 `DELETE FROM scheduled_tasks WHERE id = ?`。
  - 后果：  
    - 删除新闻任务时，可能误删 `scheduled_tasks` 中同 ID 的其他任务，或删除失败（ID 不存在）；  
    - 编辑/获取新闻任务时，`get_task` 查不到，返回“任务不存在”；  
    - 启动/停止新闻任务时，会错误地按 `scheduled_tasks` 处理。

- **问题 ST2：编辑弹窗仅适配 daily，不支持 interval/monthly**
  - 编辑表单固定为 `schedule_type: 'daily'`，只有时间、星期，无 `schedule_month_day`、`interval_minutes`。  
  - 对 `interval` 或 `monthly` 任务编辑保存后，调度类型相关配置被覆盖或丢失。

#### 2. 调度器与任务来源逻辑问题

- **问题 ST3：get_task 无法获取 news_crawl_tasks / analysis_tasks 任务**
  - `get_task(task_id)` 只执行 `SELECT * FROM scheduled_tasks WHERE id = %s`，不查 `news_crawl_tasks`、`analysis_tasks`。  
  - 编辑、更新、历史查询依赖 `get_task`，对新闻抓取、股票分析任务一律返回“不存在”。

- **问题 ST4：执行历史表仅关联 scheduled_tasks**
  - `get_task_history` 查询 `scheduled_task_history`，其 `task_id` 对应 `scheduled_tasks.id`。  
  - `news_crawl_tasks` 任务的历史可能存于其他表或结构，当前接口无法正确返回。

- **问题 ST5：analysis_tasks 删除与停止语义不清晰**
  - `delete_task` 对 `analysis_tasks` 直接返回 False，提示“股票分析任务不支持删除”。  
  - 列表仍展示 analysis_tasks，用户可点击删除/停止，但操作无实际效果，容易造成困惑。

#### 3. 创建任务与月度调度

- **问题 ST6：创建弹窗缺少 schedule_month_day 与 interval 配置**
  - 创建定时任务弹窗未提供 `schedule_type` 选择（daily/weekly/monthly/interval），也未提供 `schedule_month_day`、`interval_minutes` 输入。  
  - 后端 `create_task` 已支持 `schedule_month_day`，但前端无法配置，月度任务只能使用默认 1 号。

- **问题 ST7：创建时 task_config 与 schedule_type 可能不一致**
  - 选择“新闻抓取”等类型时，应使用 `interval`，但创建表单仍以 `daily` 时间为主，可能导致调度类型与业务不符。

#### 4. 前端交互与健壮性

- **问题 ST8：关闭弹窗使用宽泛选择器（中）**
  - `updateScheduledTask` 成功后用 `querySelectorAll('div[style*="position: fixed"]')` 关闭所有固定定位弹窗，可能误关其他无关弹窗。

- **问题 ST9：启动/停止/删除无防重复点击（低）**
  - 无 loading 或 disabled 状态，快速多次点击可能发起重复请求。

- **问题 ST10：任务类型名称映射遗漏 other_data_ 前缀（中）**
  - `getTaskTypeName` 中 `other_data_collection_*` 有映射，但实际任务类型可能是 `other_data_*`（无 `collection`），会导致显示为原始类型名，与股票数据模块问题 SD6 类似。

#### 5. 与新闻/股票数据模块的联动

- **问题 ST11：与 panel-news、panel-stock-data 的交叉操作**
  - 同一新闻任务在 panel-news 与 panel-scheduled-tasks 均可展示，若两处实现不一致（如 source 传递、删除逻辑），会出现“在此删得掉、在彼删不掉”等现象。  
  - 需统一 source 传递及后端对多来源任务的处理逻辑。
