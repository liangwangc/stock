### ✅ 3. 是否采集一个股票就存储而不是统一提交？

**结论**：✅ **是，逐条存储，不是统一提交**

#### A股数据存储方式

**存储粒度**：**逐天保存**（每个交易日一条记录）

**代码流程**：
```python
# utils/stock_history_collector.py:346-361
for i, date in enumerate(missing_dates, 1):
    # 采集单日数据
    data = self.collect_stock_daily_data(symbol, date)
    
    if data:
        # 立即保存（不是批量保存）
        if self.storage.save_stock_daily_data(symbol, date, data):
            success_count += 1
```

**说明**：
- 每个股票采集时，会循环处理每一天的数据
- 每采集完一天的数据，**立即调用 `save_stock_daily_data()` 保存**
- 每保存一条数据，都会立即执行 `INSERT/UPDATE` 并提交到数据库
- **不是等收集完整个股票或整个批次后才统一提交**

## 总结

### ✅ 优点

1. **数据存储非常详细**：
   - A股：50+字段，涵盖价格、成交、盘口、技术指标、资金流向、融资融券等
   - 美股：40+字段，涵盖价格、成交、估值、技术指标、资金流向、期权数据等

2. **实时存储到数据库**：
   - 每次保存操作都会立即执行 SQL 并提交
   - 数据实时写入，不依赖批量提交

3. **逐条存储，防止数据丢失**：
   - A股：逐天保存（每个交易日一条记录）
   - 美股：逐条保存（DataFrame 中每一行一条记录）
   - 即使程序中断，已保存的数据不会丢失

4. **进度保存机制**：
   - 每只股票收集完成后保存进度文件
   - 支持断点续传

### ⚠️ 注意事项

1. **性能考虑**：
   - 逐条保存会产生较多的数据库写入操作
   - 对于大量数据，可能会有性能开销
   - 但考虑到数据安全性和可靠性，这种设计是合理的

2. **事务处理**：
   - 目前使用的是自动提交模式（`autocommit=True`）
   - 每条 INSERT/UPDATE 都是独立事务
   - 如果需要在批量失败时回滚，可能需要调整事务策略

3. **唯一约束**：
   - 使用 `ON DUPLICATE KEY UPDATE` 处理重复数据
   - 唯一索引：`(symbol, trade_date, period_type)`

### 📝 建议

1. **保持当前设计**：
   - 逐条存储的设计在数据安全性和可靠性方面是合理的
   - 对于历史数据收集这种场景，数据不丢失比性能更重要

2. **可选优化**（如果需要提高性能）：
   - 可以考虑批量提交（如每100条提交一次）
   - 但需要权衡数据丢失风险和性能提升

3. **监控和日志**：
   - 当前已有详细的日志记录
   - 建议定期检查数据库存储情况
   - 监控存储速度和错误率
