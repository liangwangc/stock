## 二、数据获取逻辑对比

**fast_mode=True 时的优化**（`stock_history_collector.py:107-232`）：

1. **股票名称获取**：
   - ✅ 优先从数据库获取（`stock_history_data.name`）
   - ⚠️ 如果数据库没有，才调用API

2. **PE/PB数据获取**：
   - ✅ 优先从数据库获取（`_get_pe_pb_from_db_or_api`）
   - ⚠️ 如果数据库没有，才调用API

3. **历史数据获取**：
   - ✅ 优先从数据库获取90天历史数据（用于计算技术指标）
   - ✅ 当日数据从API获取
   - ⚠️ 如果数据库历史数据不足，回退到API获取

**结论**：✅ **一致** - 两者都使用相同的 fast_mode 逻辑

## 四、数据保存方式对比

### 4.1 定时任务保存方式

**单线程模式**（`scheduled_task_manager.py:822`）：
```python
result = collector.incremental_update_today(symbols, max_workers=1, batch_size=batch_size)
```
- 使用 `incremental_update_today` 方法
- 内部调用 `save_stock_daily_data`（单条保存）

**多线程模式**（`scheduled_task_manager.py:731-734`）：
```python
data = collector.collect_stock_daily_data(symbol, today, fast_mode=True)
if data:
    if collector.storage.save_stock_daily_data(symbol, today, data):
        # 单条保存
```
- 每条数据单独保存（`save_stock_daily_data`）

### 4.2 脚本保存方式

**脚本**（`update_stock_history_16_now.py:217-221`）：
```python
save_result = storage.save_stock_daily_data_batch(
    collected_data, 
    batch_size=batch_size,
    skip_existence_check=True
)
```
- 使用批量保存（`save_stock_daily_data_batch`）
- 默认批次大小：100条

**结论**：⚠️ **不一致** - 定时任务使用单条保存，脚本使用批量保存

## 六、潜在差异分析

### 6.1 数据获取时机差异

| 功能 | 定时任务 | 脚本 |

**影响**：
- ⚠️ 如果脚本在收盘前执行，获取当天数据可能不完整
- ✅ 如果脚本获取历史数据，数据完整性一致

## 七、总结

### 7.1 数据获取和计算一致性

| 项目 | 一致性 | 说明 |
|------|--------|------|
| **核心方法** | ✅ 一致 | 都使用 `collect_stock_daily_data`，且 `fast_mode=True` |
| **技术指标计算** | ✅ 一致 | 算法完全相同，都需要90天历史数据 |
| **数据字段** | ✅ 一致 | 获取的字段和计算方式相同 |
| **数据保存** | ⚠️ 不一致 | 定时任务单条保存，脚本批量保存（不影响数据内容） |

### 7.2 主要差异

1. **保存方式**：
   - 定时任务：单条保存（`save_stock_daily_data`）
   - 脚本：批量保存（`save_stock_daily_data_batch`）
   - **影响**：仅影响性能，不影响数据内容

2. **执行时机**：
   - 定时任务：收盘后执行，数据完整
   - 脚本：任意时间执行，如果获取当天数据可能不完整
   - **影响**：如果脚本在收盘前执行，当天数据可能不完整

### 7.3 建议

1. ✅ **数据一致性**：两者获取和计算的数据是一致的
2. ⚠️ **执行时机**：脚本建议在收盘后执行，确保数据完整性
3. ✅ **技术指标**：两者计算的技术指标完全一致
